TRADE_TEMPORAL_TELEMETRY_SPEC.md

1. PURPOSE

The purpose of the Trade Temporal Telemetry Engine is to record the complete lifecycle of every trade signal generated by the strategy engine.

Instead of recording only the final result of a trade (WIN / LOSS), the system records multiple temporal checkpoints before, at, and after expiry.

This allows the strategy to:

- understand why trades succeed or fail
- calibrate expiry duration
- analyze early movement vs late movement
- distinguish between bad trades and good trades with wrong expiry
- build datasets for statistical analysis and AI optimization

The telemetry engine is strictly separated from Telegram user feedback and represents the objective market truth layer for strategy evaluation.

---

2. CORE PRINCIPLE

Every "OPEN_NOW" signal emitted by the engine is treated as a virtual executed trade, regardless of whether a human user executed it manually.

This ensures:

- consistent dataset
- no dependency on user execution delay
- reliable strategy statistics

Trade lifecycle:

OPEN_NOW
 → trade registered
 → temporal checkpoints recorded
 → expiry evaluated
 → post-expiry checkpoints recorded
 → outcome classified

---

3. TRADE LIFECYCLE PHASES

Each trade passes through the following telemetry phases.

Phase 1 — Trade Registration

Triggered when strategy emits:

OPEN_NOW

Data recorded immediately:

signal_id
symbol
direction
entry_price
timestamp_open
expiry_minutes
expiry_timestamp
TPS
score_total
strategy_metadata

Trade is stored in:

/opt/binarybot/observability/open_trades_registry.json

---

Phase 2 — Pre-Expiry Checkpoints

These checkpoints observe the early health of the trade.

Purpose:

- detect early failure
- detect early success
- analyze entry timing

Required checkpoint

MID_EXPIRY

Definition:

mid_expiry_timestamp = open_timestamp + (expiry_minutes / 2)

Recorded data:

mid_expiry_price
mid_expiry_timestamp
price_delta_from_entry
direction_correct (true/false)

---

Phase 3 — Official Expiry Evaluation

This is the official outcome moment.

expiry_timestamp

Recorded:

expiry_price
expiry_timestamp
result_at_expiry

Outcome rules:

BUY

expiry_price > entry_price → WIN
expiry_price < entry_price → LOSS
expiry_price = entry_price → DRAW

SELL

expiry_price < entry_price → WIN
expiry_price > entry_price → LOSS
expiry_price = entry_price → DRAW

---

Phase 4 — Post-Expiry Telemetry

These checkpoints determine whether the trade failed due to bad signal or wrong expiry duration.

Required checkpoints:

expiry + 1 minute
expiry + 3 minutes
expiry + 5 minutes

Recorded fields:

post_1m_price
post_3m_price
post_5m_price

Derived metrics:

would_win_at_plus_1m
would_win_at_plus_3m
would_win_at_plus_5m
post_expiry_recovery

Example logic:

LOSS at expiry
WIN at +3m
→ expiry_too_short = true

5. DERIVED TEMPORAL METRICS

From the telemetry dataset the system can compute advanced trade statistics.

Early Direction Accuracy

Determines whether the trade moved correctly early.

entry → mid_expiry direction

Used to detect:

late entries
wrong timing

---

Expiry Miss Distance

Measures how close the trade was to winning.

expiry_price - entry_price

Useful for:

expiry calibration
buffer adjustment

---

Post-Expiry Recovery

Determines whether the market eventually moved in the correct direction.

LOSS at expiry
WIN at +1m or +3m

Classification:

GOOD_TRADE_BAD_EXPIRY

---

6. FAILURE CLASSIFICATION MODEL

If a trade results in "LOSS", the system attempts to classify the cause.

Possible categories:

INSUFFICIENT_SPACE
TIME_EXPIRED
SLOW_MARKET
REVERSAL_AFTER_ENTRY
SPIKE_NOISE
WRONG_DIRECTIONAL_BIAS
LATE_ENTRY_STRUCTURE
EXPIRY_TOO_SHORT

Classification uses:

space_to_buffer_ratio
speed metrics
mid_expiry direction
post-expiry checkpoints
volatility metrics

The telemetry engine must follow strict rules.

Every "OPEN_NOW" must produce exactly one outcome record.

---

Rule 2

Trade telemetry must be independent from:

Telegram feedback
manual user reports

---

Rule 3

Market price used for evaluation must come from:

strategy market feed

not user platforms.
